# 区域识别算法：现状拆解与改进方案

> 目的：把 `js/regions.js` 里"现在到底在算什么"写清楚，再按**收益 ÷ 风险**排改进项。
> 配套：`docs/auto-extract-plan.md`（§4.7–4.8 是推进记录）、`tests/regions.test.js`（现有夹具）。

## 0. 一句话概括

```
逐格取样（颜色 + 纹理） → 给每条相邻边打一个"这里是隔墙"的分 → 用区域名当种子把格子切成 k 块
→ 在 4 个候选划分里挑打分最高的 → 逐格局部搜索微调 → 输出候选区域
```

没有任何机器学习，也没有绝对颜色阈值；**唯一的"硬知识"来自图上的区域名**（k 与种子位置）。

## 2. 关键公式

**取样（每格）**：在"格内一圈"（避开中心 28% 与贴线 7%）统计 RGB 直方图 → **中位数**为格子颜色 → 转 Lab；
`edge = 强梯度像素占比`（|∇|>90）。

**格间色距**：`√(ΔL² + 2.4Δa² + 2.4Δb² + 400Δedge²)`（色度权重 2.4，纹理权重 400×Δedge²）

**隔墙判据**（每条共享边取 9 个截面，每个截面是跨线 ±6px 的亮度剖面）：
```
need   = max(22, 0.09 × 两格平均亮度)        ← 暗到多少算"墙"
暗游程 = 连续 < (格亮度 − need) 的像素数
算墙   = 暗游程 ≥ 3px 且 最深 ≥ need
coverage = 算墙的截面数 / 9
wall     = coverage × clamp((最宽游程 − 2) / 4, 0, 1)      ← 0~1
bold     = coverage ≥ 0.6
```

**划分打分**：`score = mean(wall | 跨界边) + 0.02 × mean(色距 | 跨界边)`

**层次合并**：反复合并"平均 `cost` 最小"的两个分量，直到剩 k 块。

### 2.1 Voronoi 候选：定位、原理与实测

`candidateVoronoi`（`js/regions.js:576`，全文 11 行）**不是识别算法的主角**：它只是 4 个候选
之一，负责"提议一种划分"，用不用由 `scorePartition` 决定（不参与合并、不参与打分）。

**原理**：把每个种子当成平面上的一个**站点**，每个格子归给**最近的站点**——这就是 Voronoi 图。
两个站点之间的分界是它们的**垂直平分线**，所以每一块都是若干半平面之交 → **凸块**。
代码里就是 `(r−sr)² + (c−sc)²` 取最小（整数格距、确定性、O(格数 × k)）。

**它的不可替代性**：4 个候选里只有它不是轴对齐的——
- `bands-row/col` 只能切横带/竖带，边界是整行整列的直线；
- `merge` 是贪心合并，顺序敏感、可能被衣柜/门洞的一个缺口骗过去；
- `voronoi` 不需要任何阈值，也不需要"边界必须平行于格线"这个假设。

**它也不是万能的**（用你给的 7×7 真值 + 三个种子实测，"最近种子"直接给出来）：

```
T T T T T T T        T T T T T T T
F T T T T T T        T T T T T T T
F F F T T T T   vs   F F T T T F F     ← 真值（凹口不对称）
F F F F F T T        F F F F F F F
F F F B B B B        F F F F F F F
F B B B B B B        B B B B B B B
B B B B B B B        B B B B B B B

准确率 77.6%（11 格错）；典型错误：(1,0) 判给 FRONT、(4,3)~(4,6) 判给 BACK
```

原因是它**只会画平分线**：真值的边界是横线 + 一个不对称的凹口，平分线做不到。
合成夹具里的得分也印证了这点：`merge+refine=1.083` 胜出，`voronoi=0.498` 陪跑
（凹口最终是被 `refinePartition` 的局部搜索补上的）✓

**三个固有缺陷**：
1. 距离用**格数** → 忽略 `pitchX ≠ pitchY`、旋转、透视（一行可修，按格距归一）；
2. 一个区域**只有一个种子点**，而区域名往往不在区域中心（你的图上 FRONT 的种子离真值质心
   1.01 格）→ 应该用标签 bbox 的多个格子当种子（改进项 E）；
3. **完全不用墙证据** → 只要种子稍微近一点，平分线就会直接穿过一道粗隔墙 ✗

**原理阶梯（Voronoi 在其中的位置）**：

| 档 | 方法 | 用证据吗 | 代价 |
|---|---|---|---|
| 0 | Voronoi（最近站点） | ✗ 等代价 | 11 行 |
| 1 | **测地 Voronoi / 标记分水岭**：多源 Dijkstra，边代价 = `1 − wall` | ✓ 相对证据、仍零阈值 | ~40 行 |
| 2 | 多路割 min-cut（α-expansion） | ✓ 全局最优（2-近似） | ~150 行 |

也可以从另一个角度理解：Voronoi 就是 **k-means 的分配步**；给它加上"证据权重"就变成加权
Voronoi / power diagram 或分水岭；再要求全局最优就是 min-cut（§5.3 H/I）。

### 2.2 实测：从区域名所在格"泛洪"到墙边界（watershed / 测地 Voronoi）

> 用户 2026-10-12 提问的想法：从识别到的区域名格子开始泛洪，遇到墙就停。
> 等价于图上"多源最短路"= 标记控制分水岭（marker-controlled watershed）；
> Voronoi（§2.1）就是它"所有边等代价"的退化特例。

**实验夹具**（7×7，三区颜色极接近，刻意含真实失效模式）：
木缝 3px 遍布格界；真隔墙 6px 深；**家具 44×40 跨在格界上**（制造假墙）；
**真隔墙上留 0.4 格宽的缺口**（模拟被物品遮挡）。种子 = 三个区域名所在格。

| 方案 | 家具+缺口 | 家具、墙完整 | 无家具+缺口 |
|---|---|---|---|
| 现有流水线（merge+refine） | 79.6% | 100% | 100% |
| 泛洪 **硬门槛**（wall ≥ 0.6 就禁止跨） | **44.9%** | 44.9% | — |
| 泛洪 软代价 γ=2 / 6 / 12（现证据） | 77.6% | 85.7% | 91.8% |
| 泛洪 + 局部搜索（现证据） | 79.6% | 85.7% | 100% |
| **泛洪 + 局部搜索（回落判据证据）** | **100%** | **100%** | **100%** |

同一条边的证据质量（夹具自带真值，可直接量"区分度"）：

| 证据 | 同区域内伪墙均值 | 饱和边（≥0.9） | 区分度 |
|---|---|---|---|
| 现在的 `borderProbe`（暗就算墙） | 0.40 | 30/84 | +0.60 |
| **加"回落判据"**（暗谷两端必须回到格子亮度、谷心落在格界附近） | **0.31** | **16/84** | **+0.69** |

**结论**：
1. **硬门槛不能用** ✗ 真隔墙被物品挡住时，自己的区域都到不了（44.9%）。
2. **γ 完全不敏感**（2/6/12 结果一模一样）→ 说明代价的**分辨率被证据的分辨率卡住**了；
   调 γ 是白费，要修的是证据。这和"不要再调固定阈值"的教训是同一件事。
3. 泛洪本身**不比现状强**（现证据下与现有流水线打平 79.6%），但它是**唯一能"绕过被遮挡的墙"**
   的形状机制（沿便宜路径生长，而不是要求整条边都是墙）。配合证据改造后，
   在这套最难的夹具上 79.6% → **100%** ✓
4. 透明起见：表中"回落判据"那两行里，**现有流水线仍用它自己的老证据**（它内部硬编码 `borderProbe`，
   探针改不动），所以那组比较是"泛洪 + 好证据" vs "现状 + 老证据"，两者要一起改才是完整方案。

**把证据改造正式合进 `regions.js` 之后，又量了一遍**（`/tmp/mh-probe/verify.js`）：

```
家具+缺口   100.0%（选中 merge+refine）   候选 merge+refine=1.055  voronoi=0.531  flood=0.653
家具、墙完整 100.0%（选中 merge+refine）   候选 merge+refine=1.083  voronoi=0.531  flood=0.653
无家具+缺口 100.0%（选中 merge+refine）   候选 merge+refine=1.055  voronoi=0.495  flood=0.843
```

也就是说：**决定性的那一步是"回落判据"，不是泛洪** —— 证据一修好，现有流水线自己就从
79.6% 到了 100%（它原来是被家具假墙带着从缺口漏出去的）。泛洪在这几套夹具上都不是胜者，
仍然作为第 5 个候选留在流水线里（跑一次几毫秒，不赢就不选它），
它的价值要等**真图夹具**建好之后再判：在"墙被遮挡 + 家具多"的图上，它是唯一会"绕路"的机制。

**落地形式（已实现）**：
```js
// candidateFlood：第 5 个候选，仍然让 scorePartition 挑 —— 零风险、可回退
// 多源 Dijkstra：dist[seed]=0；边代价 cost = 1 + 6*wall + 0.25*(1 - 色距/40)
```
- 前置条件（已满足）：先做 §5.1 **A/C** 让 `wall` 不再被家具污染。
- 顺手能拿到的副产品（**还没做**）：每格的 `第二近代价 − 最近代价` = **这个格子有多不确定** →
  直接当置信度，把可疑格子标出来（很符合"只给候选 + 人工兜底"的定位）。
- 工程细节：`dist=∞` 的格子按格距直线距离兜底归给最近种子；平局用确定性的扫描顺序保证可复现。
- 探针脚本：`/tmp/mh-probe/flood2.js`、`/tmp/mh-probe/verify.js`（临时目录，参数与上表一致，可重跑）。


## 3. 用你的实测数据核对：为什么现在会偏

你给的 `familymurdoku`（7×7，格距 81.9）诊断：

| 观察 | 说明什么 |

| 区域之间的边界全 `wall 1.00` | 真边界能被看见 → **信息是有的，是被平均化浪费了**；也说明"用边界证据给划分打分"方向对 |
| 区域内部也有 `wall 1.00`、色差仅 2.5 | 家具/课桌贴着格界 → 假墙。`darkFrac` 已经算出来了但**没有参与判定**（当年试过用它判定，car-repair 回退过） |
| 整体**偏一行** | 与形状算法无关：pdf.js 给的是文字**基线**坐标，视觉中心在基线上方约半格 → 种子格整体偏一格 |
| car-repair 的分界方向错 | 很可能就是 `candidateBands` 取"第一个合法组合"造成的（见 §4.1） |

结论：**先修证据层（让它不再饱和、能区分真假墙），再修种子层（偏一格），划分层最后动。**

## 4. 真 bug 与隐患

### 4.1 `candidateBands` 取第一个合法组合，而不是最好的（`js/regions.js:624`）
```js
if (ok && !bestOk) { best = assign; bestOk = true; }   // ← 谁先合法就选谁
```
组合是按分界线位置**字典序**枚举的 → 永远偏向"切得最靠上/靠左"的那种。应改为对每个
合法组合算边界代价、取最优（组合数 ≤4000，可用前缀和做到 O(1)/组合）。这是 car-repair
方向错的**首要嫌疑**，而且修起来最便宜。

### 4.2 无法采样的格子会凭空消失（`js/regions.js:74`、`:100`）
越界/过小的格子标 `ok:false` 后不进 `list`，于是**不属于任何区域**（不是被分给邻居）。
后果：换底图/裁切后边缘格可能整行消失，用户看到"区域缺一角"。应把这类格子吸附给相邻分量。

### 4.3 Voronoi 用"格数距离"，与格距比例无关（`:584`）
`(r−sr)² + (c−sc)²` 假设格子是正方形且无旋转。格距不等或底图有轻微透视时，Voronoi 候选会系统性偏。
改成像素/格距归一距离（`((r−sr)·pitchY)² + ((c−sc)·pitchX)²`）只是一行。

### 4.4 `refinePartition` 每次试搬都全量重算（`:647`）
O(轮数 × 格数 × 4 × 边数)：7×7 可忽略，20×20（400 格、1520 边）≈ 2×10⁷ 次 → 明显卡顿。
改成**增量**（只重算与该格相邻的边）→ 快 50~100 倍，顺带可以多做几轮/多起点。

### 4.5 阈值是像素与绝对亮度，不随格距/对比度走
`span 6px`、`minWidth 3px`、`depthAbs 22`、`强梯度 >90` 都是绝对值。格距 34（contest1）时 ±6px
是 ±18% 格宽（会探到邻格）；照片上阴影渐变就能满足 depth 22 → 假墙。

### 4.6 标签只取一个基线点，没有宽度
`readRegionLabels`（`js/panels.js:695`）只保留 `x, y, h`，丢掉文字宽度。一个区域名"FRONT AREA"
其实横跨 2~3 格，这些格**确定**属于该区域——现在只用了其中一个点，还因为基线偏移可能偏一格。

## 5. 改进方案

### 5.1 证据层（收益最大，建议先做）

> **A、C 已实现（2026-10-12，见 §5.5）**；B、D 待做。

**A. 墙 = "有回落的暗谷"，不是"暗"** ✅ 已实现
一条真的隔墙剖面长这样：`亮 … 暗(3~8px) … 亮`；大块家具/阴影长这样：`亮 … 暗到底`（一端不回落）。
现在只看"有没有连续暗像素"，两者都算墙。加一条**回落判据**：
```
两端亮度 ≈ 格亮度（|差| < 0.6×need）
暗谷中心落在格界附近（±max(2, 0.06×pitch) px）
⇒ 才算墙；暗但不成线的截面另记为 blocked（供诊断，不计入墙强度）
```
实测：家具造成的假墙从 `coverage 1.0 / darkFrac 1.0 / bold` 变成 `coverage ≤0.2`，
硬夹具准确率 79.6% → **100%**。

**B. 每格自己的对比度尺度**
`sampleCells` 顺便输出该格环上的亮度 **MAD / p10–p90 展布**，判据改成
`need = max(depthRel × 格亮度, 2 × MAD)`。家具/纹理重的格子自带高展布 → 需要更深的暗谷才算墙，
不需要任何新的魔法常数。

**C. 几何按格距归一** ✅ 已实现
`span = clamp(0.10 × pitch, 4, 14)`（原来固定 ±6px）；横截面位置同样按 pitch 取。
一张图在不同缩放/分辨率下结论一致（照片、不同行列数都不用重调）。
`minWidth` 仍是 3px（还没按 pitch 归一，属于 B 那类"用这张图自己的分布"的活儿）。

**D. 补一条与颜色无关、与亮度也无关的证据：两侧独立同色**
对一条边，比较"格的内部颜色"与"紧贴边界两侧各 2px 的颜色"：
若两侧贴边色都 ≈ 各自格子色，而中间有暗带 → 线；若一侧贴边就已经是暗的 → 大块暗区（不是线）。

> 注：**不要再走"调固定阈值"的路**（历史上 f079c47 用 0.4/0.6 补全墙线，反而更差，已回退）。
> 这一节所有改动都应该在 §6 的离线夹具上先量出准确率再合。

### 5.2 种子层（修"偏一行"）

**E. 用标签的 bbox，而不是一个基线点**
pdf.js 的 item 有 `width`（和 `transform` 缩放后的宽度）。取文字外接矩形 → 与网格求交 →
把这些格子都标成该区域的种子（至少用 bbox **中心**那一行）。一举三得：修 ±1 行偏移、
种子更稳、k 更可靠。

**F. 种子偏移搜索（数据驱动，不猜）**
把全部种子整体平移 `dr, dc ∈ {−1,0,1}` 共 9 种，各自跑一遍"候选 + 打分"，取分数最高的偏移。
7×7 网格上每种只要几毫秒 → 总代价可忽略。**这条能在不改任何阈值的前提下把"偏一行"自动修掉**，
而且它对"基线 vs 视觉中心"这类不确定性是免疫的（不依赖我们猜对 pdf.js 的坐标语义）。

**G. 落格外的标签吸附 + 一致性报警**
标签落在网格外 → 吸附到最近的格（而不是丢弃，丢弃会让 k 变小、两块被强行合并）；
若最终识别出的区域里有"一个区域含两个种子"或"某个种子独占一格被围住" → UI 明确提示
「区域名 X 可能没对上，请核对」，而不是静默给出错误候选。

### 5.3 划分层

**G′. 泛洪候选（2026-10-12 已实现）** ✅
`candidateFlood`：多源 Dijkstra，`cost = 1 + 6·wall + 0.25·(1 − 色距/40)`，作为**第 5 个候选**
进入 `scorePartition` 的评比（不满意时仍然由打分挑别人）。见 §2.2 的实测与 §5.5。

**H. 打分从"平均"改成"绝对和 + 非墙惩罚"**（暂未做：证据修好后，"平均"已经有区分度了）
现在是 `mean(wall)`：一个划分只要把边界放在**少数**几条墙上，平均就能很高。改成
```
cost(划分) = Σ_跨界边 [ (1 − wall) + α · exp(−色距/20) ]        // 越小越好
```
即"跨界边越少、越落在墙上越好"——长边界穿过无墙区域会被累加惩罚。这才是"墙把地图切成块"
这件事的正确能量函数（等价于一个带终端约束的**最小割**）。
2026-10-12 实测：在硬夹具上"绝对和"确实能挑对（4.03 vs 4.05），但**优势比现在的平均尺子更小**
（0.5% vs 3.7%），所以先留作备选，等真图夹具建好再决定。

**I. 真·全局划分：终端约束的多路割（min-cut）**
把每个种子当作终端（必须留在自己那块），每条边给出代价 → 求最小代价划分。
k ≤ 8、格数 ≤ 400，用 **Dinic 最大流 + α-expansion** 实现（纯 JS，约 150 行，无依赖），
几十毫秒出结果，**可以整体取代** 层次合并 + 平滑 + 4 个候选 + 局部搜索（现在这套 5 个部件）。
好处：全局最优（或 2-近似）、没有"候选挑不到"的问题、可解释（割的容量就是不可信度）。
风险：是新代码，必须先在夹具上证明比现状好再切换（保留旧路径做 fallback）。

**J. 先修 `candidateBands` 的 bug**（§4.1）：即使不改 H/I，这一步也可能直接修好 car-repair 的方向。

**K. `refinePartition` 增量打分**（§4.4）：性能上台阶，之后才敢在 20×20 上做多起点重启。

### 5.4 结果层（贴合"只给候选 + 人工兜底"的定位）

## 8. 不变的原则（来自项目已有决策）
