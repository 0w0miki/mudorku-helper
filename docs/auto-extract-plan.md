# 自动识别底图：方案与推进记录

> 这份文档是「让用户少手工搭题面」这条线的**唯一权威记录**。上下文丢失后请先读它。
> 最后更新：2026-10-11

## 1. 目标与非目标

**目标**：用户导入一张地图（PDF / 截图 / 扫描件 / 拍照）后，程序**自动**完成：
底图对位、区域划分、物品及其占格、人物名与关联，尽量省掉手工搭建。

**非目标 / 明确约束**：
- **识别永远只产出「候选」**，用户在棋盘上确认/微调后写入（可撤销）。手动兜底永远存在。
- **不维护服务器、不付算力费**：一切在浏览器里跑（静态托管或 `file://`）。
  大模型只在「用户自带 key」时可选启用，且默认关闭。
- 不追求一次识别全对；追求「省掉大部分手工 + 错了也不会把题面做错」。

## 2. 核心架构：输入适配器 + 统一栅格管线

```
输入适配器（只负责产出"好栅格 + 可选提示"）
├─ PDF      → pdf.js 渲染指定页            hints: 文字层(精确坐标)/矢量路径/图标 XObject
├─ 截图/图片 → 直接解码（粘贴/拖拽/选文件）  hints: 无
├─ 扫描件   → 同截图，通常更干净             hints: 无
└─ 拍照     → 先单应矫正，之后同截图         hints: 无
        ↓
统一栅格管线（唯一实现，与来源无关）
  0 预处理：去噪 / 暗色反转检测 / 光照归一化(照片) / 降采样
  1 几何：网格线检测 → pitch / 原点 / 倾角（P0.5 再加单应）
  2 语义提取（按可用性降级）
       ① 文字层(PDF)  ② 局部 OCR(截图/扫描)  ③ 纯视觉(颜色/纹理/形状)
  3 候选题目 JSON → 预览叠加 → 用户确认 → 走现有导入通道写入
```

**已有实测结论（重要）**：这两份官方 PDF **都有完整文字层**（`car-repair-color.pdf` 91 块、
`contest1` p1 173 / p2 108 块）——区域名、物品名、人物名、线索、`R1..R24/C1..C24` 全是带坐标的真文本。
**所以 PDF 不要 OCR**：整页 OCR 实测字符准确率仅 30-40%（装饰字体+纹理背景），文字层是 100% 且免费。

## 3. 已确认的决策

| 决策 | 内容 |
|---|---|
| 底图模型 | **保持单张**，只放**网格地图**部分（要参与对齐的只有它） |
| 图例/人物说明 | 放**右侧卡片**（现有 snipper，已支持多张/缩放/排序/持久化）；只需给卡片加轻量 `role`（图例/线索/其他） |
| 识别素材 | 识别时**按需读卡片**；识别结果不写回卡片（卡片是用户私人物品，删了不影响已识别结果） |
| 分析分辨率 | **导入时立刻分析**（原图/File 还在内存里），用**全分辨率**；压缩版(1600px)只用于显示/存档 |
| 地图被裁切 | 对位锚定在**可见网格**上（第一条检测到的线未必是 R1）；行列数由用户确认 |
| 不做 | 多底图图层（暂不做）；透视对位（P0.5）；视口大模型（可选、自带 key） |

## 4.5 P0 进度（2026-10-11）

**已完成**：几何模块 `js/align.js`（纯 JS、无依赖、Node 可测）+ 单测 `tests/align.test.js`。

算法链：降采样 → 局部背景求墨迹 → **行程长度平方加权投影**（只认长直线，纹理/文字/图标被压掉）
→ Otsu 阈值 → 归一化自相关取候选周期 → **墨迹捕获率**定周期（不受线强弱不均影响）
→ 梳状取最大精修相位 → 亚像素线位 → 最小二乘拟合 pitch/原点/倾角 → 置信度。
倾角用**投影集中度**估（网格摆正时投影最锐）；x/y 格距必须接近（正方形一致性）才算可用。

**合成图单测 8/8 通过**：干净网格、光照渐变、±18 灰阶噪声、整图旋转 2°、被裁切的地图、
纯噪声/纯白必须明确失败、真实感地图（区域纹理 + 图标 + 图例文字干扰）、性能。
真实感用例：pitch=80 精确，对比度 40、覆盖 1.0、置信度 1.0。

**真实 PDF 渲染图（4× 渲染，分析前降到 1400px 长边）**：

| 页 | 结果 | 判断 |
|---|---|---|
| `car-repair-color` p1 | ok，pitch x=70.49 / y=70.44，置信度 0.661 | ✅ 可用（15×11 可见网格） |
| `contest1` p1（人物卡页） | ok=false「x/y 格距不一致」 | ✅ 正确拒绝（不是地图页） |
| `contest1` p2（24×24 地图页） | ok，pitch x=**33.50** / y=**33.51**，置信度 0.794 | ✅ 2× 谐波已修（真值约 34） |

**已修（2026-10-11 晚）**：地图页把格距报成 2 倍。修法与原因：

1. **候选举不全**：真周期可能根本没进自相关候选（区域粗边框会让"隔一条线"的结构更强），
   所以候选里显式加入每个自相关峰的 /2、/3。
2. **判据不区分谐波**：换成 **`min(命中率, 捕获率)` 取最大** —— 约数（p/2）捕获率满分但
   一半梳齿落在空处（命中率腰斩），整倍数（2p）命中率满分但漏掉一半线（捕获率腰斩），
   只有基本周期两者都高。并列取最小 pitch。
3. **"有墨"判据必须是相对的**：横线会在每一列都留一丁点墨，`prof[i] > 0` 会让命中率永远
   满分；改成 `> 1.5 × 均值`。
4. **抛物线精修要夹住偏移**（±0.5）：`den ≈ 0` 时偏移会爆掉，pitch 变负 → 下游按 pitch
   步进的循环死循环（真把测试挂死过）。
5. **伪倾角要防**：光照渐变会估出个小角度，旋转重采样反而把线抹开 → 改成旋转前后各分析
   一次、按"两个方向都成立且置信度高"取更好的。
6. **对比度门槛 1.35 → 2.0**：纯噪声只有 1.44，会被误判成网格。
7. **用一个方向的范围限制另一个方向**：地图常只占画面一部分，图例/文字会把另一方向的
   周期带偏（`runProfile` 支持 bounds）。
8. `ratio` 门槛 0.6 → 0.4：真实地图页只有 17/30 条线足够明显，但对比度 14、两轴一致。

**剩余已知问题**：`car-repair-color` p1 的 y 方向被页面上的文字行带成半格距（x=70.49 ✓、
y=35.00 ✗，因此报"x/y 不一致"而拒绝）。这正是 **P0.1「框选地图范围」**要解决的场景——
识别只在该区域里统计；在框选功能做出来之前，这一页按"检测失败，请框选"处理即可。

**car-repair-color.pdf 的实测结论（2026-10-11 深夜，用户实测反馈）**：

这一页是**整页插画**：左边 7 张人物卡、上边标题与规则示意、右上物品图例、右下广告，
**地图是位图**、它的网格线又细又浅，四周全是深色纹理/圆角卡片/文字。投影 + 行程长度 +
梳状这条链在这一页抓不到网格：

- 整张：pitchX=53.6（contrast 5.4）但 pitchY=8.0（contrast 1.4）→ 报"x/y 不一致"**拒绝**（对的）
- 右半（地图区）：pitchX=108 / pitchY=52 → 仍是"x/y 不一致"（108 与 52 都不是真值 ~60）
- 叠加校验图（`/tmp/mh-probe/car-lines.png`）显示检出的线**跟真实格子完全不搭**
- 候选表：真值附近几个 pitch 的 capture 都在 0.31–0.41（正常应是 ~1.0）——**"墨迹"被纹理
  占满，捕获率/命中率都失去区分力**，所以不是判据问题，而是这一页的投影信号本身不干净

**结论**：位图型页面（地图是嵌入式图片、周围插画/文字密集）需要**换一套信号**——
以"长直线"为主（梯度幅值 + Hough / 线段检测，限定在框选区域内拟合点阵），
而不是逐列墨迹投影。这条留作 P0.2。

**同时补了一条不依赖识别的路径：按格定标**（`bg-calibrate`）。识别不出来时，
在地图上点三下——① 左上角格线交点 ② 右边相邻交点 ③ 下边相邻交点——直接得到
格距与原点，换算与自动对位同一套 `suggestPlacement()`。验证：合成图误差 **0.33px**。
这条路对**任何输入**都成立（位图 PDF、扫描件、拍照都能用），也是 P0.5 之前拍照档的兜底。

**P0.2 第一步（2026-10-12 凌晨）——框架有了，真实页还没翻盘**：

做了三件事：
1. **方向选择性边缘信号**：竖线的梯度必然接近水平（横线反之），先按方向筛掉 >24° 的边
   （纹理/图标的方向是乱的），再交给行程长度²加权投影；幅值阈值放低（细线对比度可能远低于
   周围插画），"短边"由**最小行程 ≥ 裁剪区 20%** 拦（网格线基本贯穿整个裁剪区）
2. **双信号择优**：墨迹信号与边缘信号各跑一遍完整的"x 定范围 → y → 回算 x"流程，
   按"两轴都成立 + 格子接近正方形 + 置信度 + 对比度"打分取更高的那组（结果里带 `signal`）
3. **两处真实假阳性修复**（都是这轮暴露的）：
   - 投影几乎为空时 `mean≈0` → `contrast=∞` 会"通过"所有门槛（纯噪声栽在这里）→
     加**证据门槛**（非零列 <4 直接判负 + 非有限/异常对比度判负）
   - `edgeProfile` 对空白图返回 null 导致崩溃 → `analyzeAxis` 加空值防御

合成图单测 12 → 13 全过，其中新增"整页插画里的位图地图"验收用例（地图块细浅线 +
四周深色卡片/文字/随机纹理）能正确检出。

**但真实 car-repair-color.pdf 仍未认出**：地图区域框选后依然是 pitch 108/52（真值约 60），
且**墨迹信号在打分中胜出**（边缘信号得分更低）。也就是说：新信号还没能在这里提供更好的
证据。下一步需要**像素级诊断**——把地图裁剪区内的边缘投影 dump 出来，看地图的线到底有没有
通过"方向筛 + 最小行程 20%"这一关（怀疑：地图地面本身有瓷砖纹理，且细线对比度接近噪声底）。
诊断脚本已就绪：`/tmp/mh-probe/p02.js`。

（当时的临时路径是「按格定标」，后来被「框地图外框」取代并已移除，见 §4.6。）

**踩过的坑（务必别再犯）**：`detectGrid()` 返回的 `cols`/`rows` 是**整幅画面**上数到的
线数（画面尺寸 ÷ 格距），**不是地图的行列数**——曾在 UI 上把它显示成"27×37 可见行列数"，
用户一眼就看出不对。地图行列数只能来自题面（用户输入）或页面文字层里的 R*/C* 标签。
UI 已改成显示"格距 xx/xpx · 缩放 xx%"，不再显示那个数。

**还没做**：P0.2 收口（像素级诊断 + 换判据）；P0.5 四角透视（拍照档）；P1 区域候选；P2 物品；P3 人物与关联；P4 额外信息。
另外「可见网格锚定」目前假定**第一条检测到的线 = 地图第一条线**（地图被裁切时用户需要
手动微调或框选），这个假定要不要在 UI 上明说，待定。

## 4.6 主路径定稿：框地图外框 + 行列数（零识别）

用户实测两个反例后定稿：

| 文件 | 现象 | 原因 |
|---|---|---|
| `car-repair-color.pdf` | 认不出（正确拒绝） | 整页插画，地图地面有**轴对齐瓷砖纹理**，投影类方法无法区分"格子线"与"瓷砖线" |
| `familymurdoku-caricature-color.pdf` | **静默错位** | 检测锚在 (972,365) —— 正是**黑板的左上角**（格距约 80px），网格从黑板往下铺 |

第二例是最坏的失败方式（ok=true 但位置错），且这份**没有 R/C 标签**（实测 rcCount=0）。
=> **自动检测网格不做**；**R/C 标签也不能依赖**。

### 主路径（不需要任何识别）

```
① 填行 / 列（题面信息，如 8×8）→ 点「生成地图」
② 点「▭ 框地图外框」→ 拖矩形正好圈住地图外框（地板区域外沿，别把黑板框进来）
③ 立即落位：原点 = 框左上角；格距 = 框宽÷列数（X）、框高÷行数（Y）；缩放 = 格子大小 ÷ 格距
④ 需要时用「对齐底图」方向键蹭最后一像素
```

**为什么稳**：只要求"框边贴着地图外框"（一眼可见），格距用**整幅跨度**算（框边差 1~2px
摊到每格可忽略），行列数来自题面——整条路没有"猜"的成分。

**验证**（含黑板诱饵的合成图：8×7 格 / pitch 70 / 地图左上角 (820,300)）：
框选后 scale 0.6286、grid=(515,189)、**网格线对齐误差 0.43px**。

## 4.7 P1 区域候选（第一版完成）

前提：底图已对位（`bg.bound` 为真，通常来自「框地图外框」）。

实现：`js/regions.js`（纯逻辑、Node 可测）

1. 逐格取样**内缩边框环**：跳过贴着格线的一圈（pad ≈ 7%）与中心核心（inset ≈ 28%）——
   中心常被家具/物品图标盖住；每通道取**中位数**而非均值，少数图标像素带不偏颜色
2. 特征：中位数 sRGB → Lab（a*/b* 权重 2.4）、亮度、以及"强梯度像素比例"（纹理）
3. 相邻格特征距离 → **Otsu 自动切阈**（同区域内距离小、跨色块边界大）→ 不需要预先知道区域数
4. 并查集连通分量 = 候选区域；再收尾：过小分量并进最相似的邻居、相邻且色差极小的分量合并
5. 一次 `commit` 写入（可撤销）；配色直接用识别到的中位色，名字默认"区域 N"

界面：区域卡片里的「🔍 自动识别区域」（有底图且已对位时才出现）。

**验证**

- 单测 4 项：3 色块 + 纹理 + 图标遮挡 / 整张同色 → 1 个区域 / 越界格不算区域 / 中位数抗图标
- 端到端（真实 app 页，合成 12×8 三色地图，每格 60px、含纹理与深色图标遮挡）：

## 4.8 P1 升级：区域名当种子（2026-10-12 晚，car-repair 已跑通）

### 关键发现：区域名就在文字层里，一次给出三样东西

区域名是画在地图上的**全大写短标签**。用"全大写 + 在地图外框内 + 字号 ≤ 半格"三个条件
一筛，`car-repair` 精确得到 4 个、`family` 得到 3 个（实测）：

### 算法：种子约束的层次合并（不需要任何绝对阈值）

```
① 每条相邻边算 cost = 颜色距离 + max(0, 线宽-2) × 线深
     —— 细网格线（宽度≤2）代价为 0；区域隔墙（≥4px）代价陡增
     —— 只需要能排序，不需要判断"多宽才算墙"（这正是之前卡住的地方：
        真实地图的砖缝与隔墙深度同量级，固定阈值分不开）
② 从最便宜的一对开始合并；**硬约束：两块都已带区域名就不许合并**（不同区域）
③ 合并到恰好剩 k 块（k = 区域名个数）；名字直接贴上去
④ 没有区域名（截图无文字层等）→ 回落到"颜色 + 粗线自适应"模式
```

**三个区域的名字与个数都对了，而且它们之间每条边的墙证据都是 1.00（完美）。**

**根因（确定）**：墙强度在这张图上饱和（55/84 条 ≥0.9），于是合并代价里
`wall × 300` 这一项对几乎所有边都是同一个值 ≈ 常数 → **排序完全由那点色差决定** →

```

  B 竖带：种子按列排序，同理
  C 最近种子（Voronoi）
打分：该划分边界上所有边的墙证据之和（越大越好）+ 各区域内部颜色一致性
取分数最高的划分
```

这比"按代价逐个合并"稳得多：墙证据在这张图上**只要用在打分上就是完美的**（分界线 1.00、
家具造成的假墙只让别的候选更差），也不会再出现"并列最强里随便挑"导致竖条 ✗。

### 4.8.6 识别区域改为「由对齐网格推出」（2026-10-12，已实现）

原先：采样范围虽然已经是从当前对齐算出来的（`regionGeometry()`），但**区域名/物品名的过滤框**
用的是框选时存下的 `MH.ui.mapBox`（原图像素坐标，只在「▭ 框地图外框」那一刻写一次）。
两个后果：

1. **框完再裁切底图**，栅格换了（`bgData` 重写、`bg.w/h`、`gridOffset` 都变），`mapBox` 还是旧坐标
   → 区域名过滤错位（贴边的名字可能被漏掉、标题可能被放进来）。
2. **只靠「对齐底图」手动对齐**的路径根本走不通：`bound` 一直是 false，识别被门槛挡住；
   而"框"本质上只负责定标，定完就该退场。

改法（不再维护第二个坐标来源）：

- `labels.areaBox(geom, pad=0.2)`：识别区域 = **当前网格矩形四周放宽 0.2 格**，纯函数、可单测。
  框选路径下 `areaBox(geom, 0)` 与手画的外框**逐像素相同**（框宽÷列数就是格距），所以判据不变。
- `labels.inBox(item, box)`：文字块是否在区域内（`pickRegionLabels` 也改用它）。
- `panels.js`：删掉 `MH.ui.mapBox`；`regionArea(geo)` 每次现算；缓存标签按**当前**区域复筛
  （缓存里的标签是上一次的框筛的，重对齐后要重筛）。
- 前提于是统一成两句话：① 网格已经对到底图上（`bg.bound`）；② 网格至少 3/4 面积压在底图上
  （`gridOnBg()`，挡住"网格在图片外面就点识别"）。
- 让 ① 在手动路径下也可达：**退出「对齐底图」模式即记下 `bound`**（提交"记录对齐"，可撤销）。

`pnpm test` 212 → 216 全过（新增 `areaBox`/`inBox` 两个单测 + 两个界面测试：
退出对齐模式记 bound、没对齐时识别只提示不写区域）。

顺带修掉一个重复点击的 bug：**识别是"重建候选"，不追加**。

### 4.8.8 截图（没有文字层）：找"区域名标签徽章"（2026-10-12，已实现）

用户导入的是**截图**（`murdoku contest.jpg`，1194×1200），没有 PDF 文字层 → 区域名读不到 →
种子里 k 也丢了 → 识别退化成"无种子"路径，碎成几十块，而且界面上没有任何提示（静默降级）。

放大看这类题面的区域名，发现是很强的视觉签名：**白底药丸 + 黑描边 + 黑字**（贴纸样式）。
于是新增 `labels.findLabelBadges(raster, pitch)`（纯函数，Node 可单测）：

1. 白掩码（`L > 阈值` 且近灰）→ 连通域；阈值在 **248/240/230/218/206/194 上各扫一遍再合并**
   —— 标签压在亮背景（白木甲板、灰石板、沙地）上时，阈值太低会和背景连成一片、太高会把药丸切碎
2. 外接框尺寸/长宽比按**格距**归一（高 0.16~0.62 格、宽 ≤5 格）→ 换分辨率不用重调
3. 框内要有**黑字**：黑像素占比 0.2~0.5，且 ≥4 个高度相近的黑字块（白抱枕/床/帆没有这个）
4. 四条边外侧 1~4px 里最暗的 1/4 像素必须是黑的（描边）——
   注意不能用"固定 3px 处的中位数"：描边只有 2~3px，压在亮底上时 3px 处已经落到背景，
   会把标签整条否掉（FRIGATE A 就是这么漏的第一版）
5. 去重：IoU ≥0.25 **或**小框被大框套住 ≥60% → 只留大的（药丸底部的碎片不再重复计）

实测（`tests/fixtures/contest-labels.jpg`，肉眼 17 个标签）：**17/17，无假阳性**，78ms。

接线：`panels.resolveLabels()` 三路取名字 —— **PDF 文字层 → 截图标签徽章 → 本地缓存**；

"没找到区域名"，不再静默降级。

已知限制：只认"白底 + 黑描边 + 黑字"这一种标签样式；深底白字或没有徽章的题面需要换判据。

### 4.8.9 截图读区域名：内置 OCR（2026-10-12，已实现）

用户明确要"OCR 识别地图上的区域名"（纯截图输入，不能假定有 PDF 文字层）。
**入口只有一个按钮**（「🔍 自动识别区域」）—— 输入类型在代码里判断，用户不需要知道：
`resolveLabels()` 按 缓存 → PDF 文字层 → 截图标签徽章(+OCR) 的顺序自己选路。方案分两步：

**① 找标签徽章**（`labels.findLabelBadges`，§4.8.8）—— 纯图形，17/17、78ms，给出**位置**。
**② 读徽章里的字**（`js/ocr.js`）—— tesseract，把 `vendor/` 里的核心与模型**按需**加载。

为什么是"内联 + 主线程"：应用从 `file://` 打开，浏览器**会挡掉 Worker 创建与 fetch/.wasm 拉取**，
所以走"经典脚本 + wasm 内联 base64 + 模型内联 base64"、在**主线程**直接调 `TessBaseAPI`
（`api.Init(null,'eng',1)` → `FS.writeFile('./eng.traineddata')` → `SetImageFile` → `Recognize`）。
两个文件共 **7.8MB**，只有点了「🔤 读区域名（OCR）」才加载，之后常驻内存；
实测整条链路 **0.6~0.8s**（17 个徽章）✓

**实测精度**（`tests/fixtures/contest-labels.jpg`，4× 放大、单行模式、只允许 A–Z）：

```
字符准确率 99.0%；整词错的只有 4 个，而且全是"词间空格"：
  CABIN A → CABINA    FRIGATE A → FRIGATEA    SLOOP A → SLOOPA    SLOOP B → SLOOPB
  （另有 SLOOP C → SLOOP CC，多了一个尾字母）
```

**补空格不靠词典，靠同一张图里的一致性**（`labels.mergeOcrNames`，纯函数、可单测）：
1. 有些徽章的空格 OCR 保住了（`CABIN B`/`FRIGATE B`/`SLOOP CC`）→ 这些前缀就是"已知词"；
   别的徽章读到 `CABINA`、`SLOOPA` 时，按"已知词 + 1~2 个尾字母"切开
2. 尾词重复收掉：`SLOOP CC` → `SLOOP C`（`CLIFF` 这种单个词不受影响）
3. 兜底才用几何（字块列间距里"最大间隔 ≥ 0.2×字高 且 ≥ 次大间隔 1.6 倍"时切一刀）

结果：**17/17 全对** ✓ 读出的名字会写进标签缓存，**再点一次按钮 25ms 走缓存、不重复 OCR**。
`pnpm test` 222 → **223**（用真实 OCR 输出做回归）；
浏览器 e2e 168 → **170** 项（一个按钮：import 截图 → 17 个标签 → OCR 17/17 个名字 → 17 个候选覆盖 576/576 格 → 再点走缓存）。

已知限制：模型只有英文（`eng`），中文题面需要另配 `chi_sim`（会再大 ~10MB，且要多加载一次）；
OCR 只用来**出候选名字**，读错在列表里改名即可。

**根因二（用户实测的真凶）：过期的"区域名记忆"挡住了更好的来源。**
自检输出暴露了它：`本地缓存：1 个` / `种子：1 个 ✗`，而同一张图上明明有 `截图标签徽章：17 个 ✓`。
老逻辑按"缓存 → PDF → 徽章"顺序取，**只要缓存非空就采用**，于是那 1 条过期标签成了唯一来源 →
种子 1 个 → 退化成无种子路径 → 整张图碎成十几块（用户看到的就是"没识别到/很碎"）。
修法：**候选名字必须能落到 ≥2 个种子上才采用**，否则继续往下找（缓存 1 条 → 徽章 17 个 + OCR）；
再加「清除记忆」按钮与自检里的说明行（`本地缓存：1 个（其中种子 1 个 → 不够 2 个，会被忽略、改用下面的来源）`）。
缓存里的坐标是原图像素、与对齐无关，所以**不再按当前框二次过滤**（那只会把好标签筛掉，落格外的由 labelsToSeeds 自然丢掉）。
缓存键也从"名字@宽"升级成"名字@宽×高 + 一小段 dataURL 采样指纹"（FNV-1a）：
同名同宽的另一张图不会再命中旧缓存；底图被裁切/换页后 `bgData` 变了 → 键变 → 自动失效。

**"点了什么都没发生"这一类问题**（用户实测遇到）——根因是"新导入的底图默认没有对位"：
`bg.bound = false` 时识别被门槛挡住，而原来只弹一个一闪而过的 toast。现在改成三件套：
1. 区域卡里**常驻**红色提示"还差一步：底图还没对位"，说清两条修法（框地图外框 / 对齐底图后退出）
2. 点「自动识别区域」时的 toast 直接写明"只会提示、不会动手"以及两条路
3. 新增「🩺 识别自检」（不需要对位就能用）：报告 底图 / 是否对位 / 网格压在底图上的比例
   （<60% 会标 ✗）/ 格距 / 区域名来源（缓存·PDF 句柄·徽章数）/ 种子数，并在条件满足时
   **让识别内核试跑一次**（不改数据），直接说"会分出几个区域"。排查"没结果"先点它。

### 4.8.10 P2 物品：**"点一个样例 → 找同类"**（2026-10-12，已实现）

- 深色图标掩码 + 贪心精确匹配：在这张密图上把 **430 格并成一块**（一次性的装饰太多，
  "最近邻距离中位数"当半径被带偏）

→ 这类地图装饰密、物品与背景叠在一起，逐格"猜哪些是物品"没有可靠判据。
**而"同一件物品是同一张画反复贴的"非常可靠**，所以改成用户点一个样例、程序找同类。

## 5. P0 详细设计

### 5.1 算法（纯 JS，无依赖，Node 可单测）

```
输入 raster = { data: Uint8ClampedArray(RGBA), width, height }, opts
1 降采样：最长边 ≤ ~1600，盒式平均（同时得到灰度 luma 与缩放比）
2 墨迹图 ink = clamp(背景 - luma, 0, 255)
    背景 = 大核盒式模糊（滑动窗口 O(W·H)）→ 对不均匀光照/照片鲁棒
3 投影：列方向累加 ink → profX；行方向 → profY
4 周期：自相关找候选 pitch（首个强峰，避免谐波）→ 再用"梳状打分"
    score(p,φ) = Σ prof[φ + k·p] 对每个候选 p 与相位 φ 求最优 → 取最高分
5 峰值精修：在 k·p+φ 附近窗口内取 ink 加权质心 → 亚像素线位；峰值太弱记为"缺线"
6 最小二乘拟合「线序号 → 线位置」→ pitch、原点、倾角；残差 RMS = 置信度
7 旋转：先由梯度方向直方图（Sobel）估计主方向（mod 90°），必要时重采样后再走 3-6
8 结果：pitch/origin/angle/可见行列数(lines)/confidence/ok
```

### 5.2 API（拟）

```js
MurdokuAlign.detectGrid(raster, { minPitch = 8, maxPitch = 400, analyzeSide = 1600 })
// → { ok, confidence, pitch: {x, y}, origin: {x, y}, angle, lines: { x: [...], y: [...] },
//     cols, rows, stats }
MurdokuAlign.toBackground(det, { cellSize, grid })   // 换算成 app 的 scale / grid.x / grid.y
```
